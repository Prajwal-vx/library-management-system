# Shelfwise security and bug audit

**Scope:** All tracked source, templates, configuration, migrations, seed scripts, and tests in the Shelfwise project. Generated caches, the local SQLite database, virtual environments, and dependency build metadata were excluded. The supplied project brief requested a full defensive review and fixes.

## Project summary

Shelfwise is a FastAPI application using SQLAlchemy and SQLite, with Jinja2/Bootstrap pages, JWT login, Argon2 password hashes, Alembic migrations, and pytest service tests. Inventory separates catalogue titles from physical copies. Circulation changes are implemented in service functions and active-loan uniqueness is backed by a partial database index.

The project starts, its seeded librarian pages render, and the current test suite passes. It remains a local/demo-oriented first version; see the remaining items below before public deployment.

## Confirmed findings and fixes

### High — reserved copies could not be issued

`app/services.py`: returning a copy could assign it to a reservation and change its status to `reserved`, while `issue_copy` accepted only `available` copies. This stranded ready holds. The issue service now checks that the selected member owns the ready hold for that exact copy, then fulfills it as part of the loan transaction. Added a regression test.

### High — members could mark their own fines as paid

`app/main.py`: the member fine endpoint changed a fine directly to `paid` without any payment processing or staff confirmation, despite online collection being out of scope. It now records `payment_requested`; staff confirm receipt before marking the fine paid. The member view explains this workflow.

### Medium — cookie-authenticated state changes lacked origin checks

`app/main.py`: browser form actions relied on cookie defaults alone. Added same-origin checks for cookie-authenticated state-changing requests and set session cookies to HttpOnly and SameSite=Strict. A cross-origin POST was verified to return 403. Configure `COOKIE_SECURE=true` when serving over HTTPS.

### Medium — softcopy upload trusted client MIME metadata

`app/main.py`: clients could label arbitrary content as PDF/EPUB. Uploads now require `.pdf` or `.epub`, enforce the configured size limit, and check basic file signatures before writing opaque names outside the static directory.

### Medium — catalogue page did repeated queries and quadratic copy scans

`app/main.py`, `app/templates/books.html`: available counts were queried once per title, all copies were loaded, and the template filtered the full copy list for each title. Replaced this with grouped count and copy queries and a per-title copy map.

### Low — member list showed the user ID as the active-loan count

`app/main.py`, `app/templates/members.html`: now computes and displays each member's active-loan count.

### Low — duplicate inventory identifiers could surface as server errors

`app/main.py`: duplicate ISBN, barcode/RFID, and member email/code conflicts now roll back and return a clear HTTP 409 response in the API instead of leaking a database error.

## Security review

- **SQL injection:** no raw SQL construction was found; queries use SQLAlchemy expressions and bound values.
- **Template XSS:** Jinja autoescaping is enabled; no unsafe HTML bypass was found in the templates.
- **Softcopy path traversal:** stored names are generated by the server, files are kept outside static assets, and resolved paths are checked before download.
- **Authorization:** API mutations use role dependencies; member account and fine endpoints check ownership. Librarian/admin page routes apply role checks.
- **Credential storage:** passwords use Argon2 via `pwdlib`; JWTs expire. Setup replaces the example signing-key placeholder with a random key; runtime also uses a random fallback if no key is configured.
- **No confirmed critical issue** was found in the reviewed code.

## Remaining issues and recommendations

- **Medium — production hardening:** HTTPS, `COOKIE_SECURE=true`, a persistent secret in a protected environment store, rate limiting for login, and security headers are not provisioned by the local setup.
- **Medium — audit history:** loans record issue actor and return date/status, but renewals and returns do not have a separate immutable event log recording the acting user and timestamp, as requested by the technical brief.
- **Medium — operations:** notifications are generated only when an admin calls the API; no scheduler or email provider is configured. The reservation hold can be checked out by a librarian through the barcode issue flow.
- **Low — auth lifecycle:** refresh tokens/password reset are not implemented; users sign in again after access-token expiry.
- **Low — dependency supply chain:** dependency ranges are declared in `pyproject.toml`, but no lockfile or automated vulnerability scan is included. Exact resolved versions were not audited against an advisory database in this pass.
- **Low — product completeness:** librarian management, shelf creation/editing, membership suspension/editing, and deaccession workflow are not exposed as complete UI workflows.
- Bootstrap is loaded from a CDN; offline use needs a local asset copy.

## Performance and UI

The catalogue N+1/quadratic lookup was fixed. No client JavaScript or 3D rendering workload exists. The interface uses responsive Bootstrap layout and the main pages rendered during checks. A full visual pass across device sizes and assistive technology was not performed.

## Tests performed

- Python compile check across app, migrations, scripts, and tests: passed.
- pytest: **6 passed** (pure/capped fine calculation, issue/return synchronization, borrowing limit, renewal limit, active-loan database uniqueness, reserved-copy pickup).
- FastAPI test client: seeded admin pages `/`, `/books`, `/members`, `/circulation`, `/fines`, `/reports` all returned 200; `/health` and `/openapi.json` returned 200.
- Cross-origin cookie-authenticated mutation check: returned 403.
- Migrations, seed, dependency advisory database scan, and responsive visual inspection were not repeated in this audit pass; earlier project setup had successfully migrated and seeded the local database.
